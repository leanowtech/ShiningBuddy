# Shining Buddy v0.9.7

v0.9.7 汇总 rc.1–rc.6 的改进，重点完善浏览器可用性、微信处理反馈、凭据恢复、WebUI 状态说明，以及定时任务和消息投递的可靠性。它是这一轮 RC 的正式版本，不另加一批业务功能。

## 定时任务：低谷执行，白天通知

- 默认仍只需设置执行时间，任务完成后按原通知策略发送结果。
- 展开定时任务编辑器的「更多设置」，可单独设置通知时间。例如凌晨 02:00 执行、上午 08:30 通知；支持每天、工作日和自定义 cron，使用任务时区。
- 执行结束后立即保存成果并释放资源，可先在 WebUI 查看。等待通知不会占用执行名额；没有新结果时不发送占位消息。
- 错过通知时点时，可等待下一个通知时间，或选择完成后立即补发。更改设置只影响后续运行，已排队或运行中的任务保留原设置。
- 延后发送的附件保存本次成果副本与内容摘要；重启后沿用通知时间，不重跑业务。副本缺失或变化时拒绝发送，保留已确认的任务成果。
- 执行状态、成果状态与通知状态分别展示。审批、凭据配置提醒和普通对话回复不受结果通知时间限制；成功或失败是否通知仍由原策略控制。

通知时间表示最早可发送时刻。服务离线、凭据锁定、通道故障或发送冷却都可能造成延后；同一任务的多次运行分别保存和通知，不自动合并。

## 微信：看得到处理，更有节奏地发送

- 恢复多任务执行时的原生「正在输入中」提示。附件准备、消息分派、业务执行和微信发起的独立专家协作共用当前绑定的状态，每 5 秒续期；一项完成不会关闭其他在途任务的提示。
- 输入状态接口故障单独恢复，不阻塞模型或正常回复，也不再误报为消息投递失败。取消、锁定、换绑和停服会清除旧状态。
- 普通回复、任务结果、审批、网页登录及控制回复统一进入持久发送队列。同账号一次发送一条，默认至少间隔两秒；图片和文件的准备单独串行，不占住已准备好文字的发送出口。
- 控制通知、交互回复和后台结果按来源轮转，避免大批后台结果长期拖住交互。明确的临时拒绝会有限退避，并遵守服务端要求的等待时间；重启保留冷却。
- 独立附件被明确拒绝后，其他附件可在冷却结束后继续发送。失败附件不自动重发；正文分片及结果未知的发送仍受顺序保护。
- 在「微信连接 → 发送管理」查看等待、暂停和冷却状态，暂停或恢复后续发送；展开「调整发送节奏」可修改间隔、退避上限和最多尝试次数。设置冲突或读取失败会保留草稿并直接显示原因。

排队不代表已经通知或手机已经收到。审批与网页登录只有在真正发出时才标记已通知，过期或已解决请求不再迟发。发出后超时、断线或崩溃的消息保留为结果待核实，不自动重复发送。`-2` 不直接等同于限流；本地默认节奏也不代表微信公布的安全额度。

## 凭据恢复：不再反复要求解锁

- 解锁后，有明确未执行记录的任务自动恢复排队。
- 已开始执行但结果尚不确定的任务，改为「待核对执行结果」，保留已有成果，不自动重跑。缺少未执行证明的旧记录同样进入待核对状态。
- 定时任务、会话和专家协作同步恢复，列表与详情自动更新；旧等待记录不再阻挡同一定时任务的下一次正常触发。
- 定时运行记录与计划发生记录一起提交，写入失败时回滚；已取消任务保持取消。微信换绑期间仍保留相应执行准入限制。

## 浏览器：修复正常任务被要求重启

- 修复定时任务的私有浏览器资料目录被误判为实例配置变更，导致 `browser_restart_required`、`web_fetch` 或浏览器读取失效的问题。
- 每个任务仍使用独立资料与输出目录；配置校验对照原始实例设置。同一定时任务连续运行可继续使用浏览器，前台、专家协作与定时执行各用对应连接。
- 实际更改浏览器配置后仍拒绝使用旧连接。结果未知的浏览器写操作不会自动重放。

## WebUI：状态更准确，内容和草稿更稳定

- 模型请求确实排队时才显示等待名额，取得名额和发出请求后分别展示实际阶段。对话中可查看占用数量、共享范围，并直达并发设置。
- 未显式配置的全实例模型请求并发上限从 3 调整为 6；保留已有明确设置和缺少来源证明的旧值。该名额由对话、微信、定时任务和专家协作共享，仍跨模型服务计数；默认独立任务数仍为 3。
- 成果或执行过程读取失败时保留已显示内容与附件，恢复后清除错误。「重新读取成果」和「重新读取执行过程」只重新读取，不重新运行业务。
- 审批记录区分批准、授权使用与任务结果；通知使用「不再提醒这条通知」，明确关闭提醒不会补发，也不改变发送结果。
- 改善任务空态、创建入口、专家与协作、工作台登录和版本维护的信息层级。登录访问令牌与浏览器批准记录分别展示，退出或撤销不会清空凭据库。
- 修复较早的权限读取覆盖后来的保存错误；返回导航后的错误与未保存草稿保持可见。相同错误再次到达时保留已展开的详情、焦点与浮层草稿。

## 升级与兼容

1. 备份原实例，正常停止旧服务，并确认已经停止。
2. 替换对应平台程序，使用原 `--data-dir` 启动。保留实例内的 `config.toml`、项目、任务、历史、浏览器资料和 Vault。
3. 首次需要更新发送记录时，启动维护页会先备份相关数据库，快照位于实例内 `maintenance/messaging-flow/`；不会因此递归复制整个实例。
4. 按页面提示解锁凭据。用 `shining-buddy --version` 核对安装程序，再用 `shining-buddy service status --data-dir /你的实例目录 --json --no-input` 确认实际运行版本为 `0.9.7`。

仅替换 CLI 不会更新已运行的旧进程。已保存的执行时间、通知时间、权限与成果继续保留；不会自动给旧任务开启延后通知，也不会批量补发已拒绝或结果未知的消息。

仅接收正式版的实例可通过现有版本检查发现 v0.9.7，无需切换到预览通道。下载仍使用官方签名清单，并需确认后执行更新。完整步骤见随包的 `UPGRADE-GUIDE.md`。

需要回退时，应先处理独立通知时间、待发通知、新格式控制通知和仍生效的暂停或冷却；不能直接替换旧程序绕过兼容检查。备份实例和保留旧程序是两件事。

## 安装包与验证范围

提供 macOS ARM64 GUI/CLI、Linux ARM64/x64 CLI，以及 Windows ARM64/x64 GUI/CLI；各平台内置对应架构的 **kvault 0.5.0-rc.1**。

macOS 使用 ad-hoc 签名，未做 Apple 公证。Linux 和 Windows 是交叉构建，尚不能视为目标机器原生运行与升级验收；正式版标签不改变这一验证边界。

发行验证使用隔离实例和合成资料，覆盖当前版本回归、真实 dsh、浏览器、启动恢复、发送断点与实际 SIGKILL、归档及 macOS 实包升级。真实用户模型表现、微信手机显示与最终送达、目标机器长期运行仍需在对应环境确认。具体构建身份、签名、摘要和平台状态见 Release 附件；公开仓库保留发行文档和安装包，不推送私有源码历史。
